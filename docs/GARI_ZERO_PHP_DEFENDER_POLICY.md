**Precedence:** **OVERRIDES ALL PREVIOUS TEST-GENERATION, SECURITY FIXTURE, OR LOGGING INSTRUCTIONS**

## 1. Absolute Zero-PHP Policy

PHP is **strictly and permanently prohibited** across the entire GARI codebase, repositories, and workflows.

### 1.1 Strict Prohibitions
Under no circumstances shall any human, AI assistant, developer tool, or automated task:
1. **Generate PHP source code** in any form.
2. **Create or retain `.php` files** anywhere in the project or system.
3. **Generate PHP payloads, webshell examples, or backdoor strings** (e.g. `eval(base64...)`, `system()`, `passthru()`, or simulated shell syntax).
4. **Create PHP-like test fixtures, mock data, or signatures**, even for the stated purpose of testing upload validation or security filters.
5. **Include PHP code snippets or examples in documentation**, commit messages, or reports.
6. **Execute PHP interpreters, PHP CLI tools, or PHP built-in servers**.
7. **Reproduce previously detected test patterns** (specifically `Backdoor:PHP/Perhetshell.B!dha` or similar detections).

### 1.2 Approved Technology Stack
All development, verification, security testing, and tooling must use exclusively:
* **Backend:** Python (FastAPI, standard libraries, safe packages).
* **Frontend:** JavaScript / TypeScript (ESM, vanilla, standard browser APIs).
* **Database:** SQL (PostgreSQL, SQLite).
* **Test Fixtures:** Harmless, structured JSON, Python dictionaries, plain text, or non-executable mock binaries.

## 2. Prohibited Artifact Generation & Log Safety

To eliminate false-positive virus detections resulting from log reflection, GARI scripts and tasks must adhere to strict artifact generation rules.

### 2.1 Prohibited Artifacts (Generated by GARI Scripts/Tests)
GARI scripts, test harnesses, and automated tools must never create or regenerate:
1. `transcript_full.jsonl` or copies containing suspicious test payloads.
2. Chunk files in `chunks/transcript_full/` containing suspicious or previously flagged content.
3. Synthetic security transcripts containing malware-like or shell-like strings.
4. Test output logs containing webshell-like or PHP signatures.
5. Unnecessary raw command transcripts or raw payload dumps.
6. Alternate copies, renamed copies, or compressed archives (`.zip`, `.tar.gz`, `.bak`) of quarantined or flagged files.

### 2.2 Antigravity System Logging Invariant
* These restrictions govern artifacts created by **GARI project scripts, tests, and tools**.
* Assistants and tools must **never** directly delete, truncate, corrupt, rename, or disable Antigravity's internal platform logging system unless an officially supported configuration explicitly permits it and the user approves.

## 3. Windows Defender Protection & Incident Protocol

Windows Defender provides essential endpoint protection and must remain fully operational at all times.

### 3.1 Strict System Invariants
* **NEVER disable Windows Defender** or tamper with real-time protection.
* **NEVER add Defender exclusions** (paths, processes, or file extensions) to bypass detections.
* **NEVER restore quarantined files** or attempt to retrieve items from quarantine.
* **NEVER manipulate Defender's internal quarantine storage** (`C:\ProgramData\Microsoft\Windows Defender\Quarantine`).
* **NEVER execute suspicious files** under any circumstance.
* **NEVER claim a machine is clean** based solely on a passing file scan without verifying active threat state.
* **STOP IMMEDIATELY** if a new Backdoor or Malware detection occurs.

### 3.2 Detection Incident Response Protocol
If Windows Defender reports a new detection during any task:
1. **Stop immediately:** Halt the running test, generation task, or build script.
2. **Preserve metadata:** Record the exact threat name, Threat ID, affected file path, and timestamp from `Get-MpThreatDetection`.
3. **Do not reproduce:** Do not copy, inspect, print, or reproduce the detected content.
4. **Report to user:** Immediately surface a high-priority incident notice to the user.
5. **Recommend native remediation:** Guide the user to run a standard **Quick Scan** or **Microsoft Defender Offline Scan** via the official Windows Security interface.
6. **Do not modify history:** Do not attempt to automatically clear, alter, or delete Windows Defender Protection History via scripts.

## 4. Safe Security Testing Guidelines

All GARI security, upload validation, and input sanitization tests must follow safe testing practices:

* **Harmless Fixtures Only:** Test file-upload filters using benign text files (e.g. `"TEST_BENIGN_INVALID_FILE_TYPE"`), empty files, or harmless mock images with invalid MIME types.
* **No Shell-Like Payloads:** Never use real or simulated executable code (PHP, JSP, ASP, EXE, ELF) as upload test payloads.
* **Structured Synthetic Data:** Use synthetic JSON structures to test validation boundaries.
* **Isolated Temporary Directories:** If test files must be written to disk, place them in temporary test folders (e.g. `tests/fixtures/temp/`) outside Antigravity's internal brain and log directories, and purge them immediately in test teardown (`tearDown()` / `finally`).

## 5. GARI Logging & Telemetry Policy

All logging within GARI application code and test scripts must be defensive and privacy-preserving:

1. **Structured Diagnostic Logging:** Log event IDs, function names, and standard HTTP/application status codes (e.g. `event_id="AUTH_LOGIN_SUCCESS" status=200`).
2. **Secret Redaction:** Automatically redact passwords, API keys, JWT access tokens, session cookies, and authorization headers from log streams.
3. **No Full Request Bodies:** Avoid logging raw HTTP request bodies on authentication or file upload endpoints.
4. **No Raw Prompt/Command Transcripts:** Avoid creating files that duplicate raw AI conversation prompts or tool command histories.
5. **No Payload Retention:** Never log or persist submitted invalid payload samples.
